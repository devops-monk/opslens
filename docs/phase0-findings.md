# Phase 0 findings (2026-11-27)

Environment: macOS arm64, Steampipe v2.5.0 (aws plugin 1.35.0 installed), Powerpipe 1.6.0, Docker 20.10.11, Python 3.13, uv, Go 1.26.
Flowpipe was **not installed**; built from the local source (see "Build note"). Spike mods now live in `tests/fixtures/mods/`.

## Questions from the plan (section 18) and answers

| # | Question | Answer |
|---|---|---|
| 3 | Does the load check fail on a broken mod? | **Yes.** `flowpipe pipeline list` exits **0** on a good mod and **255** on syntax errors, missing step references and bad param types, with a clear message and `file:line`. Verified with `tests/fixtures/mods/bad_*`. `--output json` returns the full param schema (types, defaults, enums), outputs and steps. |
| 3b | Does the data dir need to exist? | **Yes, for server mode.** `--data-dir` pointing at a missing directory makes the first run fail with "Error opening SQLite database unable to open database file". The deployer must `mkdir -p` it. The CLI load check works without it. |
| 4 | REST run flow | `POST /api/latest/pipeline/{mod.pipeline.name}/command` with `{"command":"run","args":{...}}` returns `{"flowpipe":{"execution_id","pipeline","pipeline_execution_id"}}`. `GET /process/{id}` gives status (`started`, `finished`). `GET /process/{id}/execution` gives full state; the pipeline outputs are in `pipeline_executions.<pexec>.pipeline_output`, and each step's input/output are under `step_status`. |
| 4b | Paused run (waiting for approval) | There is **no distinct "paused" status**: a run waiting on an `input` step reports `started`. The approval form URL (`/form/<id>/<hash>`) appears in the server log and in `GET /process/{id}/log/process.json`. The run tracker must detect "waiting" by scanning that event log (or the step's state), and extract the form path from it. |
| - | Catalog from REST | `GET /pipeline` returns every pipeline with steps, params and file ranges: usable for the pipeline catalog. |
| - | New files while server runs | The server's file watcher reloads mods after a short delay (about 30 s observed). Running a newly written pipeline immediately returns 404 `unknown definition not found`. The deployer must poll `GET /pipeline/{name}` until it appears before running. |
| 2 | Steampipe plugin availability | See below. |

**Consequence for the plan:** GitLab, Opsgenie and (probably) Teams reads cannot rely on official Steampipe tables.
Per plan section 12, those become `source=api` read pipelines (`http` steps) in `opslens-mod-extras`, and the catalog
marks each capability as `table` or `api`. The incident-copilot pack depends mostly on GitLab and Opsgenie reads, so this is the first extras work.

## Build note

`go build` of the local Flowpipe source failed with `pattern all:assets: no matching files found`, because the UI/docs assets are generated by the Makefile and not committed. I built from a scratch copy with an empty `assets/` directory (binary: version `v0.0.1-local.1`). The plan should use an **official release binary** (brew or the install script) for development and pin its version in `mods.lock`/docs; the local build is only a spike tool. The user's Flowpipe source tree was not modified.

## Verdict on the plan

No blockers. Three adjustments to fold into `IMPLEMENTATION_PLAN.md`:
1. Run tracker: detect approval waits from the process event log; there is no paused status.
2. Deployer: create the data dir, and wait for the server's file watcher to load new pipelines before running.
3. `opslens-mod-extras` moves earlier: GitLab, Opsgenie and Teams reads must be `http` pipelines, not tables.
